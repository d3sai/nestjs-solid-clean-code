# Request Scoping vs Singleton

## Суть підходу

NestJS керує DI-контейнером через **scope** (область життя) провайдерів. Розуміння цього механізму критичне для продуктивності застосунку.

- **Singleton (за замовчуванням).** Провайдер створюється один раз за весь час життя застосунку й повторно використовується для всіх запитів. Більшість сервісів — саме такі.
- **Request scope.** Новий екземпляр провайдера створюється на кожен вхідний запит.
- **Transient scope.** Новий екземпляр створюється щоразу, коли провайдер ін'єктується (навіть у межах одного запиту).

```ts
// Singleton — за замовчуванням, без додаткових налаштувань
@Injectable()
export class UsersService {}
```

```ts
// Request-scoped — новий екземпляр на кожен HTTP-запит
@Injectable({ scope: Scope.REQUEST })
export class RequestContextService {
  userId: string; // безпечно тримати стан, що належить конкретному запиту
}
```

## Чому це важливо для продуктивності

`REQUEST` scope суттєво впливає на продуктивність: провайдер (і весь ланцюжок класів, що його споживають) перестворюється на кожен запит, замість того, щоб існувати один раз. Під високим навантаженням це помітне навантаження на CPU/пам'ять порівняно з дефолтним Singleton-підходом.

## Коли REQUEST scope дійсно потрібен

Використовуйте `REQUEST` scope лише тоді, коли це справді необхідно — наприклад, для логування контексту конкретного користувача (user ID, request ID, tenant ID у multi-tenant застосунку) протягом усього запиту:

```ts
@Injectable({ scope: Scope.REQUEST })
export class LoggerService {
  constructor(@Inject(REQUEST) private readonly request: Request) {}

  log(message: string) {
    console.log(`[user:${this.request['userId']}] ${message}`);
  }
}
```

В усіх інших випадках варто лишатись на Singleton — це дефолт не випадково, і його варто змінювати свідомо, а не "про всяк випадок".
