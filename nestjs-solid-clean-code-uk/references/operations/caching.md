# Кешування

## Суть підходу

Кешування зберігає результат дорогої операції (запит до БД, виклик зовнішнього API) і повертає його повторно, доки дані актуальні — замість того, щоб виконувати ту саму роботу знову на кожен запит.

## `@nestjs/cache-manager` з Redis

```ts
@Module({
  imports: [
    CacheModule.registerAsync({
      useFactory: () => ({
        store: redisStore,
        host: 'localhost',
        port: 6379,
        ttl: 60, // секунди
      }),
    }),
  ],
})
export class AppModule {}
```

### Автоматичне кешування через Interceptor

```ts
@UseInterceptors(CacheInterceptor)
@CacheTTL(30)
@Get('popular-products')
getPopularProducts() {
  // результат кешується автоматично за URL як ключем
}
```

### Ручне керування кешем

Для точнішого контролю (свій ключ, інвалідація при зміні даних) кеш використовується напряму через сервіс:

```ts
@Injectable()
export class ProductService {
  constructor(
    @Inject(CACHE_MANAGER) private readonly cache: Cache,
    private readonly productRepository: ProductRepository,
  ) {}

  async getById(id: number) {
    const cacheKey = `product:${id}`;
    const cached = await this.cache.get<Product>(cacheKey);
    if (cached) return cached;

    const product = await this.productRepository.findOne(id);
    await this.cache.set(cacheKey, product, { ttl: 300 });
    return product;
  }

  async update(id: number, dto: UpdateProductDto) {
    const product = await this.productRepository.update(id, dto);
    await this.cache.del(`product:${id}`); // інвалідація при зміні даних
    return product;
  }
}
```

## Стратегії інвалідації

- **TTL (time-to-live)** — найпростіший варіант: запис у кеші сам "протухає" через N секунд. Підходить, коли невелика затримка актуальності прийнятна.
- **Явна інвалідація при записі** — кеш видаляється чи оновлюється одразу після зміни даних (як у прикладі вище). Точніше, але вимагає не забути додати інвалідацію в кожному місці, де дані змінюються.
- **Cache-aside** (показаний вище паттерн: спершу перевірити кеш, при промаху — піти в БД і покласти результат у кеш) — найпоширеніший підхід для читання.

## Де кешування доречне, а де — небезпечне

**Добре кешувати:** дані, що рідко змінюються і дорого обчислюються (каталог товарів, публічний контент, агреговані звіти).

**Небезпечно кешувати без ретельної інвалідації:** фінансові баланси, статус замовлення, будь-які дані, де застарілість може призвести до неправильного бізнес-рішення (наприклад, показати товар "в наявності", коли його вже розкупили). У таких випадках або TTL має бути дуже коротким, або кешування взагалі не варте ризику — знову ж таки, питання YAGNI (`references/principles/yagni.md`): кешування виправдане лише тоді, коли є реальна проблема продуктивності, яку воно вирішує.

## Чому це важливо

Кешування — це оптимізація, а не архітектурний принцип: воно додає ще один шар стану (закешовані дані можуть розійтись із реальними), тому впроваджується свідомо, під конкретне вузьке місце продуктивності, а не "про всяк випадок" на кожен ендпоінт.
