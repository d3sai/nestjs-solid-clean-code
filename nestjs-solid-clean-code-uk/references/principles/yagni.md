# YAGNI (You Ain't Gonna Need It)

## Суть принципу

Не реалізуйте функціонал, доки він не знадобиться насправді.

## Як застосовувати

Не пишіть «гнучкий» код «про запас». Багато розробників створюють інтерфейси чи параметри конфігурації для фіч, які ніколи не будуть впроваджені — це лише засмічує кодову базу та ускладнює підтримку.

### Приклад

```ts
// ❌ Погано: "гнучкість про запас", якої ніхто не просив
export interface NotificationOptions {
  channel: 'email' | 'sms' | 'push' | 'webhook' | 'slack'; // sms/push/webhook/slack ще не реалізовані
  retryStrategy?: 'linear' | 'exponential' | 'custom';      // жодна стратегія ще не потрібна
  priority?: 'low' | 'normal' | 'high' | 'critical';        // ніхто не використовує пріоритети
}

@Injectable()
export class NotificationService {
  send(options: NotificationOptions) {
    // насправді реалізований лише 'email', решта — мертвий код
  }
}
```

```ts
// ✅ Добре: мінімально необхідне рішення під реальну потребу сьогодні
@Injectable()
export class NotificationService {
  sendEmail(to: string, subject: string, body: string) {
    // ...
  }
}
```

Коли з'явиться реальна потреба в SMS чи push-сповіщеннях — тоді й буде видно, яка саме абстракція насправді потрібна (і чи потрібна взагалі), замість вгадування наперед.

## Філософія

Напишіть мінімально необхідне рішення, яке працює сьогодні. Потреба в масштабуванні чи гнучкості виникне пізніше — тоді й варто провести рефакторинг, спираючись на реальні вимоги, а не на припущення.

## Зв'язок з іншими розділами

YAGNI — це та сама логіка, що стоїть за питанням "чи потрібен тут Repository Pattern" (`references/data-validation/repository-pattern.md`) чи "чи потрібен тут CQRS" (`references/architecture/cqrs.md`): складна абстракція виправдана лише тоді, коли є реальна, а не гіпотетична причина для неї.
