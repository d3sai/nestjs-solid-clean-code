# Security Hardening: Helmet, CORS, Rate Limiting, секрети

## Suть підходу

Автентифікація й авторизація (`references/security/authentication.md`, `references/security/authorization.md`) захищають від того, "хто" і "що" може робити. Але production-застосунок потребує ще одного шару захисту — на рівні HTTP-транспорту та загальної гігієни даних.

## Helmet: базові HTTP-заголовки безпеки

`Helmet` виставляє набір HTTP-заголовків, що захищають від типових атак (clickjacking, MIME-sniffing, XSS через заголовки):

```ts
// main.ts
import helmet from 'helmet';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  app.use(helmet());
  await app.listen(3000);
}
```

## CORS: явний allowlist, а не `*`

```ts
// ❌ Погано: дозволяє звертатися будь-якому сайту в інтернеті
app.enableCors({ origin: '*' });
```

```ts
// ✅ Добре: явний список довірених origin
app.enableCors({
  origin: ['https://app.example.com', 'https://admin.example.com'],
  credentials: true,
});
```

`origin: '*'` у поєднанні з `credentials: true` (куки, авторизаційні заголовки) — небезпечна комбінація, яку більшість браузерів і так заблокують, але явний allowlist — це свідомий контроль, а не випадковість.

## Rate Limiting через `@nestjs/throttler`

Захищає від brute-force атак на логін, DDoS на дорогі ендпоінти та зловживання API:

```ts
@Module({
  imports: [
    ThrottlerModule.forRoot([{ ttl: 60000, limit: 10 }]), // 10 запитів на хвилину
  ],
  providers: [{ provide: APP_GUARD, useClass: ThrottlerGuard }],
})
export class AppModule {}
```

Для чутливих ендпоінтів (логін, скидання пароля) варто виставляти суворіший ліміт, ніж для решти API:

```ts
@Throttle({ default: { limit: 3, ttl: 60000 } }) // лише 3 спроби логіну на хвилину
@Post('login')
login(@Body() dto: LoginDto) { /* ... */ }
```

## Секрети та чутливі дані

- **Ніколи не хардкодити секрети** — вони живуть у `.env` і `ConfigService` (`references/architecture/configuration.md`), а не в коді.
- **Ніколи не повертати чутливі поля в response** — `passwordHash`, токени, внутрішні ID платіжних систем не мають потрапляти в DTO відповіді (`references/data-validation/dto-validation.md`).
- **Ніколи не логувати чутливі дані** — паролі, токени, номери карток, персональні дані не повинні опинитися в логах (докладніше — `references/operations/logging.md`). Це стосується і повідомлень про помилки: стек-трейс із SQL-запитом, що містить пароль у відкритому вигляді, — типова витік через логи.

### Якщо секрет уже потрапив у код чи git

"Прибрати хардкод" і "усунути ризик" — це не одне й те саме. Якщо секретний ключ (API-ключ, пароль від БД, JWT-секрет) хоч раз потрапив у коміт — сам факт видалення рядка з коду **не** робить його безпечним знову:

- Ключ лишається в git-історії назавжди (`git log -p`, будь-хто з доступом до репозиторію може його дістати), навіть після force-push чи squash, доки історію свідомо не переписали.
- Якщо репозиторій хоч раз був публічним (чи ставав публічним помилково) — вважайте ключ скомпрометованим назавжди: боти сканують GitHub на такі патерни (`sk_live_...`, `AKIA...`) постійно й автоматично.

**Що робити, якщо секрет уже "засвітився":**

1. **Негайно відкликати/перевипустити ключ** у панелі провайдера (Stripe, AWS, тощо) — це першочергова дія, ще до чистки коду. Видалений з коду, але не відкликаний ключ і далі працює для будь-кого, хто його вже скопіював.
2. Видалити хардкод із коду і перенести в `.env`/secret-менеджер.
3. За потреби — переписати git-історію (`git filter-repo` тощо) і force-push, розуміючи, що це не скасовує пункт 1 (клони репозиторію в інших людей історію не оновлять).
4. У продакшн-середовищах — використовувати спеціалізований secret-менеджер (AWS Secrets Manager, HashiCorp Vault, Doppler) замість голого `.env`-файлу на сервері, і валідувати обов'язкові змінні оточення при старті застосунку (наприклад, `ConfigModule.forRoot({ validationSchema: Joi.object({...}) })`), щоб забутий чи порожній секрет ловився одразу при деплої, а не в рантаймі.

## Захист від ін'єкцій

Використання ORM (Prisma/TypeORM) із параметризованими запитами саме собою захищає від SQL-ін'єкцій — доки немає сирих (`raw`) запитів зі склеюванням рядків:

```ts
// ❌ Небезпечно: конкатенація рядків у сирому SQL-запиті
this.dataSource.query(`SELECT * FROM users WHERE email = '${email}'`);
```

```ts
// ✅ Безпечно: параметризований запит
this.dataSource.query('SELECT * FROM users WHERE email = $1', [email]);
```

Валідація вхідних даних через `class-validator` (`references/data-validation/dto-validation.md`) додатково відсікає значення, що не відповідають очікуваному формату, ще до того, як вони дійдуть до запиту в БД.

## Чому це важливо

Жоден із цих механізмів окремо не "закриває" безпеку повністю — вони працюють шарами: DTO-валідація не заміняє rate limiting, а Helmet не заміняє авторизацію. Production-застосунок потребує всіх шарів одночасно, кожен проти свого класу атак.
