# Інструменти якості коду

## Суть підходу

Архітектурні принципи (SOLID, DRY, KISS) визначають, як писати код правильно, але не заважають комусь випадково закомітити код з іншим стилем форматування чи очевидною помилкою. Ці ризики закривають автоматизовані інструменти, що запускаються до того, як код потрапить у спільну гілку.

## ESLint + Prettier

- **ESLint** — статичний аналіз коду: знаходить потенційні помилки (невикористані змінні, `any` без потреби, порушення правил проєкту).
- **Prettier** — автоматичне форматування: прибирає суперечки на кшталт "табуляція чи пробіли" з рев'ю коду, бо стиль просто уніфікується інструментом.

```json
// .eslintrc базово вже йде з NestJS CLI-шаблоном, типове доповнення:
{
  "rules": {
    "@typescript-eslint/no-unused-vars": "error",
    "@typescript-eslint/explicit-function-return-type": "off"
  }
}
```

## Husky + lint-staged: pre-commit hooks

Запускає лінтер і форматування автоматично перед кожним комітом — лише для змінених файлів, щоб перевірка була швидкою:

```json
// package.json
{
  "lint-staged": {
    "*.ts": ["eslint --fix", "prettier --write"]
  }
}
```

```bash
npx husky init
echo "npx lint-staged" > .husky/pre-commit
```

Якщо файл не проходить лінтер — коміт блокується локально, до того, як проблемний код взагалі потрапить у репозиторій чи CI.

## Conventional Commits

Стандартизований формат повідомлень коміту (`feat:`, `fix:`, `refactor:`, `chore:`) дозволяє автоматично генерувати CHANGELOG і визначати версію за семантичним версіюванням у CI/CD pipeline:

```
feat(orders): add idempotency key support for order creation
fix(auth): correctly reject expired refresh tokens
refactor(users): extract notification logic into separate service
```

## Чому це важливо

- **Консистентність без суперечок.** Стиль коду перестає бути предметом обговорення в code review — Prettier вирішує це автоматично, а ревʼювер фокусується на логіці, а не на форматуванні.
- **Раннє виявлення помилок.** ESLint ловить частину проблем (невикористані імпорти, підозрілі патерни) ще до рантайму, задовго до того, як вони дійдуть до тестів чи проду.
- **Масштабування команди.** Що більша команда — то дорожче обходиться відсутність таких інструментів: без них стиль коду неминуче розходиться між розробниками, а помилки, які лінтер зловив би миттєво, доходять до code review чи й до продакшену.
